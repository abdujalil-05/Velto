# Ручная приёмка закрытого пилота v0.9

> 2026-11-01, ветка `feat/approved-decisions`. Для Product Owner и тестировщиков. Тут только проверки, которые **не заменяются** автотестами (TZ §16.5: проваленный ручной тест не перекрывается покрытием unit-тестами).
> Правило: результат ставит только тот, кто проверку **выполнил**. Пустой результат = NOT_TESTED. Агенты и разработчики PASS не ставят.
> Стенд: только изолированный, только синтетические данные (`docs/release/PILOT-STAND-PLAN.md`). На каждую проверку записать build SHA стенда.

## Общие предусловия

- Стенд запущен, `GET /health/ready` → 200, `checks` все `up`; SHA сборки записан.
- Синтетическая компания A и B (`bootstrap-owner.ts`), коды для подключения MFA выданы (`issue-mfa-enrollment-code.ts`) и записаны в журнал выдачи.
- Доказательства складываются в `docs/qa/evidence/<дата>/<ID>/` (скриншоты, jobId, HTTP-ответ, выписка из `/audit`). Реальные телефоны, ФИО и пароли в доказательства не попадают.

Формат результата в каждой проверке: `PASS` / `FAIL (+ что увидели)` / `BLOCKED (+ причина)`.

## 1. MFA ADR-058: четыре ручных сценария (условие A1)

Источник: `docs/parity/ADR-058-MANUAL-CHECKLIST.md` (итоговые отметки ставятся там же).

### M1. Реальное приложение-аутентификатор: подключение и вход
- **Предусловия:** пользователь OWNER без MFA; выдан код подключения; телефон с Google Authenticator или Aegis; время на телефоне синхронизировано.
- **Действия:** войти по паролю → ввести код подключения → отсканировать QR телефоном → ввести 6-значный код → сохранить recovery-коды → выйти → снова войти паролем + кодом из приложения.
- **Ожидается:** QR читается; код принимается; 10 recovery-кодов показаны **один раз** (после обновления страницы их нет); повторный вход требует TOTP; без кода токены не выдаются.
- **Доказательство:** скриншоты экранов (QR и коды замазать), запись `auth.mfa.enroll*` в `/audit`.
- **Результат:** ____ **Ответственный:** PO

### M2. Привилегированная роль в Telegram Mini App
- **Предусловия:** бот и Mini App настроены на стенд (HTTPS); пользователь с ролью OWNER, SALES_DIRECTOR или CASHIER привязан к Telegram.
- **Действия:** открыть Mini App в реальном Telegram (Android и iOS).
- **Ожидается:** вход отклонён, `403 MFA_WEB_LOGIN_REQUIRED`, понятный текст на uz/ru; обойти MFA через Telegram нельзя.
- **Доказательство:** скриншоты с обеих платформ + версия Telegram.
- **Результат:** ____ **Ответственный:** QA

### M3. Mini App: истёкшая сессия и отзыв после сброса MFA
- **Предусловия:** агент (SALES_AGENT) в Mini App, в офлайн-очереди 1–2 неотправленных заказа.
- **Действия:** (a) дождаться истечения сессии или отозвать refresh; (b) OWNER сбрасывает агенту сессии/MFA в web; агент продолжает работу.
- **Ожидается:** сообщение «Сессия истекла», повторный вход; **очередь сохраняется**, после входа заказы уходят ровно один раз.
- **Доказательство:** скриншоты до и после, номера заказов на сервере (без дублей).
- **Результат:** ____ **Ответственный:** QA

### M4. Повтор TOTP-кода в том же 30-секундном окне
- **Предусловия:** OWNER с MFA; второй пользователь с MFA для step-up сброса.
- **Действия:** войти кодом X; в течение тех же 30 с выйти и войти тем же X. Повторить для step-up «Сбросить MFA» у сотрудника.
- **Ожидается:** второй ввод отклонён (`lastUsedStep`); в `/audit` есть запись об отказе; сброс не выполнен.
- **Доказательство:** скриншоты ошибок, записи аудита.
- **Результат:** ____ **Ответственный:** PO

## 3. Excel и S3-совместимое хранилище, запрет ACK (условие A3)

- **Предусловия:** стенд с реальным MinIO (или иным S3-совместимым), bucket приватный, политика из `deploy/minio-policy.json`; есть закрытый день с 2–3 внутренними счетами.
- **Действия:**
  1. `/export/1c` → формат EXCEL, период до вчера → создать.
  2. Дождаться GENERATED, скачать файл, проверить SHA-256 (экран против `X-Content-SHA256`).
  3. Убедиться, что в UI нет кнопки ACK.
  4. Прямой `POST .../ack` для этого job → ответ.
  5. Анонимный запрос к объекту в MinIO и листинг bucket.
  6. Пользователь компании B запрашивает jobId компании A.
- **Ожидается:** файл в MinIO, помечен «Не для импорта в 1С»; ACK нет; API → `409 1C_EXPORT_REGISTER_NOT_ACKNOWLEDGEABLE`; анонимный доступ и листинг → 403; компания B → 404 без раскрытия.
- **Доказательство:** jobId, SHA-256, скриншоты, HTTP-ответы, ключ объекта в MinIO.
- **Результат:** ____ **Ответственный:** QA
- **Важно:** успешный EXCEL **не является** доказательством интеграции с 1С.

## 5. Android и iPhone по OFFLINE-DEVICE-MATRIX (условие A6)

Источник: `docs/OFFLINE-DEVICE-MATRIX.md`, сценарии S1–S15, колонки A / I / T-A / T-i / L, сети normal и intermittent 2G/3G. Отметки ставятся **в матрице**, рядом точная версия ОС, Telegram и браузера.

- **Предусловия от PO:** список реальных устройств агентов пилота (модель, ОС, версия Telegram), одно low/mid Android, способ ограничить сеть, иконки PWA для S13.
- **Минимум платформ:** `crypto.randomUUID` и `crypto.subtle` (шифрование очереди) работают только в secure context, то есть по HTTPS или на localhost. На iOS нужен Safari/WKWebView 15.4 или новее, на Android WebView/Chrome 92 или новее. Устройство ниже этих версий → BLOCKED и замена устройства, обходной генератор не допускается.
- **Обязательные для v0.9:** S1, S2, S3, S4, S5, S6, S7, S9, S10, S15 на T-A и T-i; S8, S12 на L.
- **Результат по матрице:** ____ **Ответственный:** Field Ops + QA
