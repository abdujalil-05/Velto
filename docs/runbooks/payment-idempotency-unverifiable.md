# Payment idempotency UNVERIFIABLE / CONFLICT (same clientId, original not provable)
- **Detection:** `POST /payments` answers 409 `PAYMENT_IDEMPOTENCY_UNVERIFIABLE` (or `PAYMENT_IDEMPOTENCY_CONFLICT`), `details.clientId`; `POST /sync/push` returns the item as `REJECTED` with the same `error.code`. Server keeps an append-only `AuditLog` row `action='payment.create_rejected'`, `entity='Payment'`, `entityId` = the EXISTING payment, `newValue.reason` = the code (written after rollback, ADR-061). On the device the document stays in the Mini App queue as `FAILED` with `lastError.code` and is listed under "Needs attention" on `/queue`. Alert: (planned).
- **Severity:** SEV3 per document (no money was written by the rejected request); SEV2 if several agents/customers are affected or a balance drift is found in step 2.
- **Triage (PO-approved manual reconciliation; the strategy is final — no code path "auto-heals" it):**
  1. **Who:** an authorized employee only — Customer Accountant / Cashier with `payments.read`, `cash.read`, `invoices.read`, `customers.read`; corrective actions need the permission named in step 4. Check the **source document** (paper receipt / PKO / bank or card confirmation), the **cash session** that received the money (`GET /cash-sessions`, web `/cash`; the payment's `handoverCashSessionId`), and the agent's device copy (step 6).
  2. **Reconcile** the existing payment (find it by `clientId` from `details.clientId`): `GET /payments/:id`, `GET /payments`, `GET /payments/in-transit` (agent cash not yet accepted), `GET /invoices`, `GET /invoices/:id`, `GET /customers/:id/balance` (web `/customers/[id]`), `GET /reports/aging` (as-of date explicit), `GET /reconciliation/findings` (kind `BALANCE`; web `/reconciliation`), `GET /audit` (web `/audit`; list only, no filters in MVP). Read-only SQL as `velto_app` inside a tenant tx (`SET LOCAL app.current_company_id = '<companyId>'`), SELECT only:
     `SELECT id, number, "customerId", amount, method, status, source, "collectedBy", "clientId", "handoverCashSessionId", "handoverRejectReason", "createdAt" FROM "Payment" WHERE "clientId" = '<clientId>';`
     `SELECT "invoiceId", amount, "createdAt" FROM "PaymentAllocation" WHERE "paymentId" = '<paymentId>';`
     `SELECT reason, "actorId", "createdAt" FROM "PaymentReversal" WHERE "reversesPaymentId" = '<paymentId>';`
     `SELECT action, "userId", "newValue", "traceId", "createdAt" FROM "AuditLog" WHERE entity = 'Payment' AND "entityId" = '<paymentId>' ORDER BY "createdAt";`
     `SELECT "cachedBalance" FROM "Customer" WHERE id = '<customerId>';` — compare with invoices − live allocations − advances (see [allocation-mismatch](allocation-mismatch.md)).
     Compare amount / method / customer / intended invoices with the source document and the device copy. Missing allocation rows prove nothing (they are not evidence that the original was a FIFO request).
  3. **Already posted ⇒ no new payment.** If the existing payment (POSTED, or PENDING_HANDOVER awaiting the cashier) is the same money as the source document, it IS the payment: do not create another one, neither in web `/payments/new` nor by re-entering it on the device. If only the invoice split differs, use `POST /payments/:id/allocate` (`payments.allocate`, distributes the unallocated advance, audited `payment.allocate` mode `MANUAL_LATER`); allocations already made are not moved.
  4. **Real financial error ⇒ only existing authorized, audited operations:** wrong posted payment → `POST /payments/:id/reverse` (`payments.reverse`, reason required, `@Idempotent`, writes `PaymentReversal` + audit; web `/cash`), then — only if money was really received — a new payment entered by the cashier from the source document; wrong agent cash still in transit → `POST /payments/:id/handover/reject` (`payments.handover`, reason) or accept it with `POST /payments/:id/handover/accept` (open cash session required); cash-desk difference → recorded at `POST /cash-sessions/:id/close` (`cash.close`); `cachedBalance` projection drift → `POST /reconciliation/run` + `POST /reconciliation/findings/:id/fix` (`reconciliation.fix`, audited).
  5. **Never** `UPDATE`/`DELETE` on `Payment`, `PaymentAllocation`, `PaymentReversal`, `Invoice`, `AuditLog` (AuditLog is trigger-protected), never re-use or edit a `clientId`, never insert a payment by SQL.
  6. **Keep the original offline record until resolved.** It lives in the agent's Mini App IndexedDB (Dexie table `queue`, key `clientId`) encrypted with the agent's per-user+company vault key (AES-GCM, format `uk1`; the vault key is wrapped by the server KEK from `GET /auth/offline-kek` and is never stored unwrapped). It stays `FAILED`/held with `lastError`, is never auto-retried, pruned or re-sent, and survives logout (also offline logout): after logout no other account on the device can decrypt it; it reappears only when the same user of the same company logs in online. The agent/operator sees it on Mini App `/queue` ("Needs attention"). The agent must NOT re-enter the payment. Server side there is no copy of the rejected payload — only the `payment.create_rejected` audit row; capture the device copy (screenshot of the queue card: customer, amount, method, created time, clientId) for the case.
  7. **Record the result:** OWNER or CASHIER files the decision in web `/reconciliation` → "Offline payment conflicts" (`POST /payments/reconciliations`, `payments.handover`): `EXISTING_PAYMENT_CONFIRMED` or `NOT_POSTED_CONFIRMED` (document reference required). One decision per `clientId`; the same decision again is idempotent, a different one → 409. The decision writes `PaymentIntentResolution` + AuditLog only (no Payment/allocation/ledger change). After it the agent's app removes the held record automatically on the next online session; a record is never removed without this server-confirmed status (emergency wipe is the only exception, with an explicit confirmation).
- **Data safety:** the rejected request wrote nothing (thrown before any write, tx rolled back). Payments/allocations/reversals are append-only; corrections only via the operations in step 4.
- **Owner:** Customer Accountant (decision) + Cashier (cash session) + Tech Lead (evidence/SQL).
- **Verification:** exactly one live payment for the source document; `GET /customers/:id/balance` and `GET /reconciliation/findings` show no BALANCE drift after `POST /reconciliation/run`; Σ allocations ≤ payment amount; ticket filed; device record discarded only after that.
- **Comms:** agent and Sales Director informed of the outcome (no re-entry / re-entered by cashier); Accountant gets the ticket.

**Ticket template:** `clientId` · existing `Payment.id` / `number` · customer id · amount / method (server vs device vs source document) · source document no./date · cash session id · outcome (`SAME_PAYMENT_NO_ACTION` / `ALLOCATED` / `REVERSED_AND_REENTERED` / `HANDOVER_REJECTED` / `OTHER`) · corrective document ids (reversal, new payment, reconciliation finding) · operator (user id + role) · reason · resolved at (UTC+5) · device record discarded at.
