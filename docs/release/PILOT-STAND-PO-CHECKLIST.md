## 1. Что купить или предоставить (PO)
1. VPS (раздел 2) у провайдера, допустимого юристом (раздел 7, локализация ПДн).
2. Приватное S3-совместимое хранилище для приложения (раздел 3) — либо управляемое у провайдера, либо MinIO/SeaweedFS на том же VPS (строка 15 матрицы: выбор PO).
3. Отдельное offsite-хранилище для бэкапов у **другого** аккаунта/провайдера, чем VPS и S3 приложения (раздел 4).
4. Домен (или поддомен) и доступ к его DNS (раздел 5).
5. Канал аварийных алертов: отдельный Telegram-бот + чат ответственного (не бизнес-бот), желательно второй канал (email/webhook) — `MONITORING-ACCEPTANCE-CHECKLIST.md` §GAP.
6. Внешний uptime-сервис (проба снаружи VPS, интервал 1 мин).
7. Для ручной приёмки: Telegram-бот стенда, Android и iPhone пилотных агентов, бухгалтер клиента с образцами 1С.

## 2. VPS — минимум
| Параметр | Минимум |
|---|---|
| CPU / RAM / диск | 4 vCPU / 8 ГБ / ≥120 ГБ NVMe |
| ОС | Ubuntu 24.04 LTS, публичный статический IPv4 |
| Доступ | SSH по ключу, root-доступ на время установки, консоль провайдера (VNC/serial) на случай потери SSH |
| Провайдер | снапшоты диска; firewall на уровне провайдера (желательно); исходящий трафик к S3/offsite/Telegram не заблокирован; известная скорость uplink (нужна для RPO, раздел 8) |
| ПО (ставим сами) | Node.js 22 LTS (≥22.12 <27), PostgreSQL 16, Redis 7 (AOF, `noeviction`), nginx + certbot, PM2 (fork) |

## 3. S3 для приложения — обязательные свойства
- S3 API с подписью SigV4, path-style или virtual-host (настраивается в env), HTTPS.
- Приватный bucket: анонимный доступ запрещён (кроме `products/*`, `deploy/minio-policy.json`); проверка — анонимный HEAD → 401/403.
- Отдельный ключ приложения, ограниченный одним bucket (не root/admin) — `PILOT-RUNTIME-SECRETS-CHECKLIST.md` S5.
- Версионирование (желательно) — защита объектов от перезаписи/удаления; иначе только архив объектов в бэкапе (`BACKUP-RESTORE-RUNBOOK.md` B.6).
- Расположение данных — по заключению юриста.

## 4. Offsite-backup — гарантии от провайдера
- Отдельный аккаунт/провайдер (другой failure domain, чем VPS).
- **Versioning + Object Lock** (Compliance или Governance), retention ≥30 дней; lifecycle-удаление после 60–90 дней настраивает владелец, не сервер.
- IAM-политики на уровне prefix: три идентичности — server-put (только `PutObject`, на сервере), restore-read (только чтение, хранится вне сервера), admin (политики/lock, не на сервере). Запрет Delete/PutBucketPolicy/PutObjectRetention/BypassGovernance для server-put — `BACKUP-RESTORE-RUNBOOK.md` B.3–B.5.
- Ответ провайдера: нужен ли `ListBucket` для загрузки (проверяется на стенде, B.4).
- Если Object Lock не поддерживается — PO письменно принимает остаточный риск (компрометация сервера → удаление копий).

## 5. DNS и HTTPS — что нужно
- Имя хоста стенда (например, `pilot.<домен>`), A-запись на IPv4 VPS (AAAA — только если IPv6 настроен).
- Доступ к DNS-панели или человек, который внесёт запись; TTL ≤300 с на время запуска.
- Email для Let's Encrypt (уведомления о сертификате); порт 80 открыт для HTTP-01 (или DNS-01 через API регистратора).
- После выпуска: HSTS включается только после проверки, что HTTPS работает на всех путях (`PILOT-DEPLOYMENT-RUNBOOK.md`).

## 6. Доступы и секреты к подготовке
- SSH-ключи администраторов (публичные), список людей с доступом.
- ОС-пользователи разделены: deploy, runtime (PM2), backup (root-юнит), monitor — `PILOT-SERVER-REQUIREMENTS.md` §5.
- Генерируются **на сервере**, в репозиторий/чат не передаются: JWT, `MFA_ENCRYPTION_KEY`, KEK, пароли ролей PostgreSQL (`velto_owner`, `velto_app`, `velto_system`, `velto_backup`, monitor), Redis `requirepass`, gpg-passphrase бэкапа — полный список и места хранения: `PILOT-RUNTIME-SECRETS-CHECKLIST.md` §4.
- Предоставляются PO: ключ S3 приложения, offsite server-put ключ, токен аварийного бота + chat id, токен бота стенда (Telegram Mini App), реквизиты внешнего uptime-сервиса.
- Escrow (хранится вне сервера у PO): gpg-passphrase бэкапа, offsite restore-read ключ, `MFA_ENCRYPTION_KEY` (без него MFA-секреты не расшифровать после восстановления).
- **`velto_backup` — привилегированные учётные данные.** Роль не может писать (204/204 DML запрещены), но имеет BYPASSRLS и **читает данные всех компаний**. Пароль — только в `/etc/velto/backup.env` (root, 0600), никогда в env приложения/PM2; `pg_hba` ограничивает источник локальным хостом; ротация при любой подозрительной активности и при смене состава администраторов (ADR-066).

## 8. Методика измерения RPO/RTO (синтетика на пилотном стенде)
Цели: RPO ≤1 ч, RTO ≤4 ч. **Не подтверждены.** Ежечасный дамп сам по себе RPO ≤1 ч не доказывает.

**Данные.** Синтетический тенант-набор, сопоставимый с ожидаемым объёмом пилота через 6–12 мес.: 3+ компании, все ~100 таблиц со связями и индексами (через `seed`/генератор, не одна широкая таблица), объекты в S3 реального размера (фото/импорт/экспорт). Зафиксировать: размер БД, размер bucket, число объектов.

**RPO** = максимальный возраст последней *восстановимой offsite*-копии в момент аварии:
`RPO_факт = интервал запуска + длительность backup-run (dump+gpg+verify) + время offsite-загрузки + (для объектов) длительность архива объектов`.
Замер: 24 ч подряд с ежечасным таймером; для каждого прогона из status-файла взять `ts` (начало снимка) и `offsite_ts` (подтверждение offsite); RPO_max = max(offsite_ts[i+1] − ts[i]) по суткам + учесть пропущенные/упавшие прогоны. PASS только если RPO_max ≤60 мин для БД **и** отдельное решение PO по RPO объектов (`RPO-RTO-ASSESSMENT.md` §4). Если не укладывается — выбор PO: интервал 30 мин или WAL/PITR (§3, вариант B/C).

**RTO** = от объявления аварии до первого успешного входа пользователя на восстановленной системе. Секундомер по этапам: (1) новый VPS/чистая ОС, (2) установка ПО по runbook, (3) загрузка архива из offsite restore-read ключом, (4) gpg-расшифровка + `pg_restore`, (5) роли (`provision-roles.sql -v velto_env=production`) и `migrate deploy`, (6) восстановление объектов S3, (7) секреты из escrow, старт PM2, (8) DNS/TLS, (9) smoke: вход, tenant isolation, сверка counts/md5 с исходником. PASS только если сумма ≤4 ч, выполнял человек по runbook без помощи разработчика, протокол с временами — в `docs/qa/`.

**Целостность.** После restore: counts + md5 по всем таблицам, 3 компании совпадают, AuditLog append-only, RLS включён (FORCE), вход под каждой ролью.

## 9. Приёмка аварийных уведомлений
Обязательные проверки и способ имитации — `MONITORING-ACCEPTANCE-CHECKLIST.md` (строки 1–13): API недоступен, PostgreSQL, Redis, S3, неуспешный backup, нет свежей offsite-копии, зависшие задачи, PM2 restart loop, диск, TLS. Порог offsite для ежечасного таймера: `MONITOR_OFFSITE_MAX_AGE_MINUTES=180` (сейчас 1560 — только для суточного).
Процедура: окно работ согласовано, получатель предупреждён → имитация сбоя → в протокол: время сбоя, время получения, **кто получил (человек подтверждает)**, текст без ПДн, время RECOVERED. **PASS только после реального получения алерта ответственным человеком**; dry-run и логи скрипта — не доказательство.
Открытые GAP (функции не добавляются без решения PO): BullMQ stalled/active (сейчас только failed/wait-счётчики), внешний uptime-провайдер, второй канал.
