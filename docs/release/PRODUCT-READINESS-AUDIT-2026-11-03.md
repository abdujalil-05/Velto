## 3. Локальный E2E (HTTP, компании A и B) — все PASS

Сотрудник+MFA → клиент+точка → визит (VERIFIED / OUTSIDE_RADIUS) → заказ (серверная цена, client unitPrice игнорируется) →
confirm + Idempotency-Key (4 параллельных = 1 резерв) → недостаточный остаток 409 → 2 параллельных confirm без oversell →
отмена → полная и частичная доставка (6/10) → счёт → оплата 1 500 000 FIFO (INV1/INV2 PAID, INV3 PARTIALLY_PAID) →
переплата → аванс → сторно (оригинал сохраняется) → handover → aging/sales/dashboard/CSV.
Негативные: 403 ×6 + audit `auth.permission_denied`, 401; sync push ×3 одним clientId = 1 заказ; 20 документов ×2 параллельно = +20;
PRICE_CHANGED → CONFLICT; batch 21 → 400; 3 параллельных deliver = 1 счёт; A↔B: 7 эндпоинтов + sync/pull → 404/пусто.
Сверка: счета − POSTED оплаты = Customer.cachedBalance = API balance. Финансовых расхождений нет.
Не выполнено: падение Redis (Redis общий), MinIO недоступен (storage health down), реальный Telegram и устройства.

## 6. Критический путь «вход → оплата»

1. OWNER: вход + MFA → создаёт сотрудников (агент, директор, склад, кассир, курьер) → Telegram-привязка.
2. OWNER: товары, упаковки, прайс → клиенты и точки → **начальные долги (D6: нет пути в UI)** → маршрут агента.
3. Агент (Mini App): маршрут → визит → заказ (offline допустим) → sync. **M1: ошибки сохранения не видны.**
4. Директор: /orders/[id] → confirm (резерв). **D2: агент может обойти этот шаг.**
5. Директор или склад: назначение курьера. **D3: нет UI** → обходной путь: склад отгружает сам через диалог доставки.
6. Склад или курьер: доставка, полная или частичная → счёт.
7. Агент или кассир: оплата → FIFO по счетам → handover → кассир принимает → долг уменьшается.
8. Директор или бухгалтер: aging, отчёты, экспорт 1С (BLOCKED_EXTERNAL).

Путь проходит до оплаты без терминала, если использовать обходной путь на шаге 5 и не вводить начальные долги.
